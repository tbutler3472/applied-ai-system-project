# Game Glitch Investigator

Game Glitch Investigator started as my Module 1 number-guessing game. I found
bugs with reversed higher/lower hints, secret numbers outside the selected
difficulty ranges, and incorrect difficulty settings. For Project 4, I extended
that game with a RAG Strategy Coach, an AI Strategy Agent, and validation and
reliability checks.

## Overview

This project is a Streamlit number-guessing game for CodePath AI. The game runs
locally and does not need an API key.

The player selects a difficulty, enters guesses, and receives **Too High**, **Too Low**, or a win message. The app also shows Hot/Warm/Cold feedback, a score, remaining attempts, and guess history.

## Difficulty settings

- **Easy:** 1–20, with 6 attempts.
- **Normal:** 1–50, with 8 attempts.
- **Hard:** 1–100, with 5 attempts.

A submitted guess must be an integer inside the selected range. Invalid or out-of-range guesses do not count as attempts.

## RAG Strategy Coach

The **Ask AI for Strategy** button starts a RAG-style coach flow:

1. Python narrows the public range using each guess outcome.
2. The app calculates the remaining possible numbers, attempts left, guarantee status, and an unused midpoint guess.
3. Retrieval matches the player's difficulty and clues against `data/guessing_strategies.json`.
4. Retrieved source text is sent to local Ollama along with the public game facts.
5. The model writes a short player-facing explanation.

The strategy knowledge base contains documents for midpoint and binary-search use, both higher/lower clue types, repeated guesses, and each difficulty. The app uses keyword matching and prioritizes entries that match the selected difficulty. The **View Retrieved Strategy Sources** section shows the retrieved titles, IDs, and text.

The custom knowledge base helps the coach use advice that fits the player's
current state. For an Easy opening, retrieval can bring in Easy, midpoint, and
binary-search tips. After a Too High clue, it can retrieve advice about lowering
the upper bound. Without retrieval, the model would only have general guessing
advice in its prompt; with retrieval, it also receives these specific strategy
notes. This is a qualitative difference in the information provided to the
model, not a measured improvement over a baseline.

The coach is grounded in public facts only. Its displayed bounds and recommended guess are calculated by Python, not generated by the model. Ollama cannot see or change the secret number.

## AI Strategy Agent

The **Ask AI Agent** button uses a separate agent workflow. Local Ollama receives a tool-selection prompt and chooses from the available read-only tools:

- `analyze_range`: find the remaining range and number of possibilities.
- `review_guess_history`: find repeats and whether earlier clues were efficient.
- `evaluate_attempts`: check attempts left and whether a win can be guaranteed.
- `retrieve_strategy`: retrieve relevant entries from the strategy knowledge base.
- `recommend_next_guess`: find an unused midpoint choice in the remaining range.

Ollama returns an ordered tool plan with a short reason for each choice. The app parses the JSON response, rejects unknown tools or unsafe arguments, and executes only the fixed Python functions above. The plan can contain fewer than five tools; the app never runs more than five. Ollama cannot run shell commands or change the game state.

If the model does not include an acceptable summary in its initial response, the app sends the validated game facts and executed tool results in a separate final-explanation request. Python checks the resulting explanation for internal claims, hidden-answer guesses, incorrect attempt counts, impossible guarantees, bad ranges, repeated guesses, and unsupported recommendations. If the check fails, the app displays a natural deterministic fallback. The **Agent Decision Trace** expander shows the selected tool, reason, and structured result for each step.

## Validation and deterministic fallback

Several checks protect the application:

- History must contain valid guesses and known outcomes.
- Tool plans must be JSON objects with allowed tool names and empty arguments.
- Unknown tools, malformed JSON, extra fields, and unsafe requests are rejected.
- A final model explanation must match the validated range, history, attempts, and recommendation.
- Ollama connection failures and request timeouts use local fallback text.
- The agent has a 30-second overall time budget and reserves time for the final explanation.

A fallback means Python still provides the correct next guess and game analysis. It does not mean the model successfully produced an explanation.

## Setup

### 1. Create a virtual environment

Windows PowerShell:

```powershell
py -3.13 -m venv .venv
.\.venv\Scripts\Activate.ps1
```

Python 3.10 or newer is required. The commands above create a Python 3.13
virtual environment.

### 2. Install Ollama and the model

Install Ollama for your operating system, then start the Ollama service and pull the model:

```shell
ollama pull llama3.2:3b
ollama serve
```

On Windows, Ollama may already be running after installation; run
`ollama serve` only if the service is not already running. The app expects
Ollama at `http://localhost:11434`. Ollama is optional for playing the game
and running automated tests.

### 3. Install Python dependencies

```shell
python -m pip install -r requirements.txt
```

### 4. Start Streamlit

```shell
python -m streamlit run app.py
```

Open the local address printed by Streamlit. Use a new terminal to keep Ollama running if needed.

## Testing

Run all automated tests:

```shell
python -m pytest -v
```

The tests mock Ollama, so they do not require the local model. They cover game mechanics, difficulty ranges, RAG retrieval, validation, tool selection, execution, malformed responses, timeouts, and fallback behavior.

Run the reproducible Project 4 evaluation:

```shell
python evaluate.py
```

This does not require Ollama. An optional local-model smoke test can be attempted with:

```shell
python evaluate.py --ollama
```

The optional smoke test does not change the required pass/fail summary. Ollama
availability and latency can vary.

## Known limitations

- Ollama latency varies by computer and model loading time. The app uses request timeouts and a total agent budget, but an explanation can still take too long.
- A successful tool-selection request does not guarantee a successful final explanation. Timeout or validation fallback is intentional.
- The RAG retrieval uses lightweight keyword and source filtering rather than embeddings or a vector database.
- Ollama is a local text model, not an authoritative calculation service. Python remains responsible for all numeric results.
- Streamlit behavior is covered by automated AppTest checks, but this README does not claim that every UI screen was manually tested.

## Selected AI capabilities

**RAG** uses the local JSON strategy knowledge base to retrieve relevant guidance before Ollama writes an explanation. **Agentic workflow** lets Ollama choose among bounded read-only tools, while fixed Python code executes and validates the results. This project combines model-selected tool use with deterministic safeguards rather than trusting generated numbers directly.
